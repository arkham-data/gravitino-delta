# Delta Spark Production Runtime Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox syntax for tracking.

**Goal:** Deliver an optional Spark 3.5 runtime that resolves Delta registrations through the production Gravitino provider and delegates native transactions to Delta.

**Architecture:** A composed native DeltaCatalog preserves DeltaTableV2 identity. A lazy staged descriptor chooses the tested SCHEMA_ONLY or QUERY binding before reservation, then journals typed intent before POST and the production receipt before native construction, commits natively and publishes through ordinary client transport. String-only discovery keeps the default runtime independent of Delta.

**Spec:** `docs/superpowers/specs/2026-09-08-delta-production-runtime-design.md`

**Dependencies:** Reviewed native metadata, closed schema-contract characterization, and production provider/wire plans. Interface names below must be reconciled with their committed results before dispatch. This is a pending plan, not evidence of implemented behavior.

## Global Constraints

- No core, API, server, client, or storage-schema source changes.
- Spark 3.5.4/3.5.6 and Delta 3.3.0/3.3.2, Scala 2.12. Explicit production deltaSparkVersion/deltaVersion properties default to 3.5.4/3.3.0 and reject other values; converge all org.apache.spark dependencies in the optional module configurations. Production build settings are separate from fixture opt-in settings.
- Native Spark/Delta/Scala/Hadoop classes are provided and never relocated. No server provider, Kernel, embedded server or test fixture in the Spark runtime.
- Gravitino owns names and immutable admitted locations. No Glue registration and no session-catalog table registration as a hidden second authority.
- Marker/receipt identity is not authorization, writer fencing or a complete query/data digest. Current client identity is resolved per operation through the existing catalog manager.
- No blind POST retry after uncertain completion. STATUS does not prove the original owner hook ended; recovery requires confirmed request completion/drain before an operator-controlled pending replay.
- No physical cleanup on ambiguous native failure; preserve the operation receipt for reconciliation. No unsupported operation may silently mutate Delta before reporting its admission failure.
- One source/Gradle owner at a time. No implementer subagents, shared deployment, push, merge or PR creation. Root owns local services and private credentials.

### Task 1: Implement production transport, journal and native catalog adapter

**Files:**
- Create `spark-connector/v3.5/spark-delta/build.gradle.kts` and register `:spark-connector:spark-delta-3.5` in `settings.gradle.kts`.
- Production package `org.apache.gravitino.spark.connector.delta`: `GravitinoDeltaCatalogSpark35`, `DeltaRegistrationClient`, `DeltaRegistrationJournal`, `DeltaPublicationStage`, `DeltaReplacementStage`, `DeltaRegistryDelegate`, and `DeltaCatalogProperties` (split further only when distinct responsibility warrants it).
- Corresponding focused tests in the new module, using injected transport/journal seams instead of static server callbacks.

**Interfaces:** `GravitinoDeltaCatalogSpark35 implements StagingTableCatalog, SupportsNamespaces, AutoCloseable`. Public initialize/name/namespace and table methods implement native Spark interfaces. Delegate loaded tables remain actual `DeltaTableV2`, including version/timestamp overloads. Registration transport uses production shared command and receipt values through normal public Gravitino TableCatalog APIs. Journal records sanitized typed command intent before any mutating request, then the bound receipt and phase before native mutation, durably via atomic replacement/fsync in an explicitly configured driver-owned local directory; injected in-memory journal is unit-test-only. The durable intent is exactly the typed production command (schema/contract, token, run and applicable expected identity), not a wholesale Spark property/option map. No credentials or arbitrary native properties enter the journal. A lost POST response retains the original request/token/run and unknown registration ID rather than inventing success.

Prove journal failure prevents native stage construction; uncertain POST never retries CREATE automatically; intent-journal failure prevents POST itself. Use constructor-injected native stage factory/transport to observe ordering and failures.
- [ ] **Step 2: Implement transport and durable journal.** Resolve `GravitinoCatalogManager.get().getGravitinoCatalogInfo(name)` for the current caller on each catalog operation; preserve its client lifecycle. Validate all receipt bindings against the submitted request before using location/marker. Perform authoritative published lookup and expected-ID/generation transition. Existing CREATE conflicts; missing REPLACE fails. BEGIN_REPLACE response loss uses its next-generation/new-token STATUS; POST uncertainty records status-needed and returns a sanitized recovery error. Use the read-only named-table statusByToken(token,writerRunId) form when allocated ID is unknown; expected-ID checks remain mandatory for mutations. Missing initial ownership may require privileged administrative STATUS through existing REST gates. Expose a narrow production operator helper using the same transport for STATUS/HANDOFF/PUBLISH/ABORT; no direct entity store or fabricated stop proof. Journal contains request-completion uncertainty explicitly, uses restrictive permissions and bounded decoding, and does not delete pending evidence on abort.
- [ ] **Step 3: Implement lazy native staging.** Capture stable declared descriptor fields and expose native expected V1_BATCH_WRITE, plus TRUNCATE only for replacement routes. `newWriteBuilder` selects QUERY using the characterized resolved schema normalization; untouched commit selects SCHEMA_ONLY. Validate mapping mode (including session defaults), excluded native metadata/options and internal max-ID overrides before reservation. Use exact v1 or the reviewed v2 contract, never postcommit rebinding. After durable reservation/journal, create native stage using server location and marker in the same native transaction. Existing schema-only COR uses native stageReplace; absent schema-only COR uses native stageCreate after server-authoritative absence/reservation. This avoids unsupported v1 CREATE OR REPLACE TABLE evidence without changing the published CREATE/REPLACE identity checks. Keep native writer result and native commit unchanged. Publish only after native commit; postcommit publication failure retains receipt and native data. Abort after reservation does not automatically issue privileged ABORT or claim rollback.
- [ ] **Step 4: Implement named reads and namespace delegation.** Install a complete native delegate through DeltaCatalog.setDelegateCatalog before any native call, because native path loading calls super.loadTable first. Its path lookup must throw the expected NoSuchTableException to allow native path fallback; it must never register a second session-catalog table. Every named lookup obtains a fresh published provider observation before constructing the native path identifier. Preserve native DeltaTableV2 and time-travel loading, native append/overwrite/INSERT/UPDATE/DELETE/MERGE paths. Implement one-level namespace delegation and consistent Spark exceptions. Namespace mutation is governed by provider policy, including retained hidden rows on cascade. Implement actual cache invalidation using native delegates where meaningful; never cache a pending receipt as a published table. Route unsupported registration drop/purge/rename with explicit early errors while later lifecycle semantics remain unqualified. Implement outer alterTable explicitly: prevalidate the entire change list (including reserved location/marker/internal mapping changes) before the first native mutation, resolve the authorized location, dispatch admitted native changes through DeltaCatalog.alterTable(pathIdentifier, changes), and reload through Gravitino for metadata refresh. Native Delta ALTER may commit individual grouped changes independently; do not invent all-or-nothing atomicity for a list. For native ALTER/RESTORE schema evolution, verify ordinary provider refresh sees updated metadata; do not manually publish a new operation after ordinary DML.
