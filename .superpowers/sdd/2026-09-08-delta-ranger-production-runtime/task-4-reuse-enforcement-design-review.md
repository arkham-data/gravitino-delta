# Independent review: reused SELECT execution guard

Reviewed the proposed design and production sources at `88478f00896c65d157f5f0d688bc0a59140bd543` on 2026-09-21. This is a source review, not implementation or qualification. No code changes, tests, Gradle, JVM, services, Docker, or commits were run. Only this report was written. No callable claude-mem/mcp-search tool was available; existing local design evidence was read instead.

**Verdict: approve a narrower ordinary unary action guard as the first implementation design; do not approve the opaque leaf proposal as implementation-ready.** Qualify only repeated `Dataset.collect`/`collectAsList` over the existing admitted SELECT shapes with user AQE explicitly unsupported. The complete receipt, cache-rejection and typed-native-provenance requirements below remain mandatory before production acceptance. `injectColumnar` is an injection seam rather than a general action authorization API. No core/API/server/client/schema changes appear necessary.

## Preferred first slice: visible unary action guard

Use an ordinary `UnaryExecNode` without `CodegenSupport`. Override `executeCollect` to validate the complete receipt before calling `super.executeCollect()` or the child's collection entry. The child stays visible to the remaining codegen/reuse passes and the inherited cleanup/metric-reset traversal. `Dataset.collect` and `collectAsList` call `withAction`, which resets metrics and then calls `collectFromPlan`; that helper dynamically dispatches `plan.executeCollect()`. It does not call `prepare()` before that dispatch. Both pinned sources expose non-final `executeCollect`. [Spark 3.5.4 Dataset](https://raw.githubusercontent.com/apache/spark/v3.5.4/sql/core/src/main/scala/org/apache/spark/sql/Dataset.scala), `collect`, `collectAsList`, `withAction`, `collectFromPlan`; [Spark 3.5.4 SparkPlan](https://raw.githubusercontent.com/apache/spark/v3.5.4/sql/core/src/main/scala/org/apache/spark/sql/execution/SparkPlan.scala), `executeCollect`.

No mandatory dispatch bypass was found for those two Dataset methods. `SQLExecution.withNewExecutionId` does produce plan descriptions/info before entering the action body. It does not itself prepare or execute the user physical child; physical guard coverage therefore still needs the existing analysis/pre-CBO protections for planning and native metadata work. Arbitrary listeners/extensions remain trusted launcher code. [SQLExecution](https://raw.githubusercontent.com/apache/spark/v3.5.6/sql/core/src/main/scala/org/apache/spark/sql/execution/SQLExecution.scala), `withNewExecutionId`.

An `executeCollectPublic` override can validate before forwarding, although its base implementation dynamically calls `executeCollect` already. Public `executeToIterator`, `executeTake` and `executeTail` can also be overridden if later included in a precise method contract. Do not add them to the first qualification claim merely because they compile. `executeCollectIterator` is `private[spark]`, unnecessary for these Dataset collection paths, and should remain outside the first supported surface rather than forcing a package bridge. Pin compilation of all chosen overrides.

Keep `doExecute`/`doExecuteColumnar` validation as defense in depth, but **do not claim that this unary guard validates raw physical execution before child preparation**: final `execute`, `executeColumnar`, `executeBroadcast` call recursive preparation first. Direct raw plan entry, direct `prepare`, `QueryExecution.toRdd`, RDD retention and iterator consumption are explicitly unsupported trusted-code escapes. This limitation is essential to the narrower design's approval.

The unchanged controls must show the wrapper remains the actual executed-plan root after normal tail passes and that its overridden collection entry runs once per collection action, including after earlier success. Check the complete parent receipt before any child collection/preparation; never place the only action guard inside a join subtree. The opaque-leaf findings below explain why the broader physical-entry guarantee should remain deferred; the visible unary choice removes the hidden-tail-pass and cleanup-bridge obligations.

## Blocking corrections

### 1. Specify exactly what is hidden and who finishes preparing it

The proposed “already prepared delegate” is ambiguous. In both pinned versions, the physical rule pipeline runs columnar transitions **before** `CollapseCodegenStages` and `ReuseExchangeAndSubquery`. A leaf installed in the post-columnar callback hides its delegate from those remaining passes. It must not call the full `QueryExecution.prepareExecutedPlan` recursively: that applies the same columnar extension again. Nor may construction eagerly call `delegate.prepare()` to compensate. These are different kinds of preparation. [Spark 3.5.4 QueryExecution](https://raw.githubusercontent.com/apache/spark/v3.5.4/sql/core/src/main/scala/org/apache/spark/sql/execution/QueryExecution.scala), `preparations` and `prepareExecutedPlan`.

Choose and document an exact pipeline: finish the required remaining physical transformations once on the delegate using a qualified optional-module adapter, or explicitly qualify the finite delegate shapes without those transformations. The latter can change performance and plan behavior and requires unchanged-result controls with ordinary codegen settings. A codegen passthrough guard that disappears into generated code is unacceptable. `CollapseCodegenStages` traverses ordinary children; it will not repair a hidden tree later. [Spark codegen rule](https://raw.githubusercontent.com/apache/spark/v3.5.6/sql/core/src/main/scala/org/apache/spark/sql/execution/WholeStageCodegenExec.scala), `insertWholeStageCodegen`.

State the invariant as: **the envelope has no executable children or subquery expressions, and its preparation does not prepare or execute the delegate; every supported execution entry validates the whole retained receipt before touching the delegate.** `doPrepare` alone is insufficient. `executeQuery` invokes preparation before `doExecute`; preparation recurses into children and runs `doPrepare` only once. The leaf proposal avoids that recursion only if it really keeps the delegate opaque. [Spark 3.5.6 SparkPlan](https://raw.githubusercontent.com/apache/spark/v3.5.6/sql/core/src/main/scala/org/apache/spark/sql/execution/SparkPlan.scala), `executeQuery`, `prepare`.

An instrumented broadcast child is mandatory: its `doPrepare` starts its relation future, which can collect input asynchronously. A stale join must fail before either child's preparation, including after the envelope has previously been prepared successfully. [BroadcastExchangeExec](https://raw.githubusercontent.com/apache/spark/v3.5.6/sql/core/src/main/scala/org/apache/spark/sql/execution/exchange/BroadcastExchangeExec.scala), `relationFuture`, `doPrepare`.

### 2. Resolve lifecycle and access visibility rather than promising generic forwarding

Specify output, ordering, partitioning, row/columnar support, metric reset, cleanup, canonicalization, cloning and serialization behavior. Spark's default cleanup and metric reset walk children, so hiding the delegate removes that propagation. `cleanupResources` is `protected[sql]`; an arbitrary `SparkPlan` delegate cannot simply be called from the existing `org.apache.gravitino...` Scala package as if this were a public forwarding method. Qualify a narrow adapter/bridge inside the optional artifact, or a bounded lifecycle alternative. Do not introduce reflection as an unreviewed workaround. [Spark 3.5.4 SparkPlan](https://raw.githubusercontent.com/apache/spark/v3.5.4/sql/core/src/main/scala/org/apache/spark/sql/execution/SparkPlan.scala), `resetMetrics`, `cleanupResources`.

Receipts/validators must remain driver-owned, excluded from task closures, plan text and JSON display. Avoid a global strong-reference plan map with no lifecycle. If the envelope is cloned, the new physical delegate must retain a valid receipt binding; a copied opaque ticket alone cannot bless arbitrary scans. Test failure cleanup and successful repeated execution, not just denial counters.

### 3. Make the action boundary an explicit allowlist

For the first slice, claim `Dataset.collect` and `collectAsList`, rather than all SQL/DataFrame actions or raw physical entries. `collect` reenters the executed plan; `foreach` and `foreachPartition` use `rdd`. `head`/`take`, `tail` and `count` construct derived limit/aggregate plans, which the current finite admission can reject independently of the execution guard. An unrelated unsupported-shape exception is not guard coverage. Retained iterator consumption also does not reenter the guard. [Dataset](https://raw.githubusercontent.com/apache/spark/v3.5.6/sql/core/src/main/scala/org/apache/spark/sql/Dataset.scala), `foreach`, `foreachPartition`, `head`, `collect`, `count`, `rdd`, `toLocalIterator`.

`QueryExecution.toRdd` is lazy and retains the result of the first `executedPlan.execute()`. Therefore a subsequent action on that same RDD can bypass repeated plan entry, even when the RDD has never yet computed a partition. Document the boundary at returning the RDD/iterator, not merely at returning rows. Keep direct `toRdd`, Dataset RDD APIs, retained iterators and custom driver code under the explicit trusted-launcher contract. [Spark 3.5.6 QueryExecution](https://raw.githubusercontent.com/apache/spark/v3.5.6/sql/core/src/main/scala/org/apache/spark/sql/execution/QueryExecution.scala), `toRdd`.

Choose whether the wrapper inherits base collection methods or forwards to the delegate's optimized collection methods. Every forwarding override must validate before delegation; otherwise `executeCollect` can bypass `doExecute`. Include `executeTake(0)` if claiming denial for every action rather than only entries capable of returning user data. Do not claim RDD job or iterator revocation.

### 4. Resolve AQE and native-plan discrimination before installing a global rule

The smallest credible slice should explicitly reject **user** AQE plans until an outer boundary is implemented and proven. Do not silently change `spark.sql.adaptive.enabled`. A blanket session-level AQE rejection also risks rejecting typed native Delta metadata work. For later AQE support, the outer wrapper must precede adaptive materialization and survive final-plan reuse. Stage-only wrapping is insufficient: adaptive collection has its own entry path, and post-stage columnar rules must preserve shuffle/broadcast root types. [AdaptiveSparkPlanExec](https://raw.githubusercontent.com/apache/spark/v3.5.6/sql/core/src/main/scala/org/apache/spark/sql/execution/adaptive/AdaptiveSparkPlanExec.scala), `postStageCreationRules`, `newQueryStage`, `executeCollect`, `withFinalPlanUpdate`.

The current local `DeltaRangerPlanAdmission.scala:107` admits several native logical shapes using a live `NativeScope`; `registerSnapshot:66` records exact RDD/output lineage. The physical callback may run after that scope ends. Calling `internalMetadata(logicalLink)` later is not a sufficient general classifier, and “no user receipt means internal” is unsafe. Specify typed native provenance captured while the original admission is valid and bound to the owning snapshot/operation. Missing or mixed provenance rejects. Native log-file indices, state reconstruction, aggregate binding and cached native lineage need positive tests both within and after scope; copied markers and ordinary JSON/Parquet must remain negative.

The 3.5.4 SparkPlan/QueryExecution/Columnar source seams were directly readable in this review. The 3.5.4 SparkSessionExtensions page was not retrievable, so that public injection signature still needs pinned compilation/runtime proof. Source inspection does not qualify either Delta version.

### 5. Turn the receipt proposal into one complete comparison protocol

The existing read-rule root tag retains only short user name/groups (`DeltaRangerReadRule.scala:68`); `check`/`prepare` only inspect that marker. The existing engine `Versions` retains service/definition and numeric policy/role values, while `snapshot()` finishes by checking policy context but not role object/version stability a second time (`DeltaRangerPolicyEngine.java:428`). Retaining those existing objects unchanged is insufficient.

Define an immutable analysis receipt and the entry protocol before editing the guard:

1. Capture actual current subject/groups and all owning catalog/engine leases. Capture full validated completed policy publication and independent role publication identities, including same-number replacement detection and trusted service/definition/metalake binding.
2. Retain original per-scan canonical resources and exact original columns before masking/filter rewriting. Include every scan occurrence and engine in joins. Reauthorize that original set at entry; compare all retained mask kinds/expressions and row-filter outcomes, including absence. Rechecking SELECT permission alone cannot validate already rewritten rows. Entry evaluation must not rewrite the retained plan.
3. Read each canonical registration through the distinct scoped metadata supplier; require PUBLISHED state, same incarnation/location/native UUID and compatible admitted schema. Capture bindings around the native named load, then associate them with the actual returned descriptor/scan. At entry compare current metadata to the retained scan binding, not a newly synthesized path identity.
4. Sample the complete subject/engine/role and registration validation batch consistently enough to reject observed drift. Metadata I/O must not leave an earlier engine/lease check as the final check. Use deterministic publication barriers in tests. Preserve the explicitly stated limitation: an update after the admitted execution boundary does not cancel the already started action.

This is implementable within the optional connector: `GravitinoDeltaCatalogSpark35.load` already loads through the metadata supplier and returns native `DeltaTableV2`, and the receipt decoder is public in `delta-common`. However, `DeltaTableIdentity.attach` currently discards incarnation information and the base class's registry helpers are package-private. The Ranger subclass needs its own scoped binding mechanism using existing public surfaces; a name/path-only map would recreate the gap.

`DeltaRangerPolicyEngine.evaluate` sets current access time. Decision comparison or explicit rejection of unsupported time-sensitive features is required even when version stamps agree. Add value comparison for `MaskDecision` rather than relying on current object identity. Preserve the current original-access-before-rewrite order in `DeltaRangerMaskRules`.

## Smallest implementable RED/GREEN sequence

**Mechanics slice, explicitly not security completion:** implement the visible unary action guard and root injection rule, using a deterministic driver validator seam in tests. Prove a real DataFrame `collect` reaches its collection-entry validator on both first and repeated entry under normal Spark settings. Start AQE-off by explicit test configuration. Instrument a child with prepare/execute counters; retain the Dataset and physical plan, change validation state, and invoke `collect` again, asserting both counters stay unchanged. Include positive repeated execution, row and vectorized native scans, broadcast-capable joins, cleanup, and an explicit unsupported-AQE negative. Raw physical `execute` is not the pre-prepare assertion target. The RED must demonstrate the existing retained-plan gap; merely testing a helper's boolean comparison is inadequate. This component may establish mechanics while task 4 remains open.

**First production vertical slice:** wire the complete receipt protocol above into one admitted named Delta projection/filter SELECT and repeated `collect`/`collectAsList`. Capture provenance before optimization and validate again before `PrepareDeltaScan` in pre-CBO, then at the unary guard's collection entry before child preparation. Include stale subject/groups, same-number context replacement, policy revoke, role-only change, changed mask/filter, registration replacement/pending/missing, schema drift, metadata lease expiry and engine closure. Every stale case needs an unchanged control and a guard-specific denial assertion. Add a two-catalog/broadcast test before claiming the already admitted join surface remains supported.

Reject user cache substitutions explicitly at the post-substitution logical boundary and again in physical admission, including nested hits. Never set cache configuration off or rely on cache invalidation to hide missing provenance. Keep native metadata caches on their existing typed route. This slice proves cache rejection, not safe cache reuse.

Finish qualification separately against real Ranger 2.8.0 downloads on Spark 3.5.4/3.5.6 × Delta 3.3.0/3.3.2, with exact rows/denials and engine state before/after. The fresh-query same-JVM harness is independent evidence and cannot establish retained-plan enforcement. Neither these slices nor this review close full Delta conformance, AQE support, cache reuse, arbitrary RDD security, or task 4 as a whole.
